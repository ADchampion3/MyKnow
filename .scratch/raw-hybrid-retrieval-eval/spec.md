# Raw Hybrid Retrieval Deterministic Evaluation

Status: ready-for-agent
Label: ready-for-agent

## Problem Statement

MyKnow already has a raw retrieval channel that combines keyword recall and optional vector recall with reciprocal rank fusion. The system exposes ranked raw child chunks, including keyword rank, vector rank, and RRF score, but there is no durable evaluation suite that quantifies whether the right chunks are retrieved or how well they are ordered.

The current request is deliberately narrower than a full RAG evaluation. LLM answer generation, LLM-as-a-judge metrics, answer faithfulness, answer relevancy, tracing, and hosted evaluation are not part of this work. The first useful signal is the retrieval quality of the raw channel itself.

The runtime database currently has no evaluation corpus or qrels. Runtime data is also separate from the data that should be reviewed and versioned as an evaluation artifact. A reproducible evaluation boundary is therefore needed before real qrels are supplied.

## Solution

Add a standalone DeepEval TypeScript evaluation suite for raw hybrid retrieval. The suite will invoke the existing retrieval orchestration at its highest useful seam, build an isolated SQLite fixture from versioned evaluation data, run the real keyword and vector retrieval paths, and score the returned raw child chunk ranking with deterministic metrics.

The suite will report Recall@K, Hit Rate@K, MRR@K, and NDCG@K for K values 1, 3, 5, and 10. Relevance will be defined at raw child chunk level with graded qrels. Corpus embeddings will be prepared explicitly with the configured real embedding provider; query embeddings will be generated by that provider during evaluation. No mock fallback is allowed for a real-provider run.

The evaluation data-generation method is intentionally left open. The implementation must consume the agreed data contract without deciding how the user later creates the corpus, queries, or qrels.

## User Stories

1. As a MyKnow developer, I want to run a raw hybrid retrieval evaluation from the repository, so that retrieval regressions are visible before changes are accepted.
2. As a MyKnow developer, I want the evaluation to exercise the real raw retrieval orchestration, so that the result reflects production ranking behavior rather than a copied test implementation.
3. As a MyKnow developer, I want to evaluate raw retrieval independently from answer generation, so that retrieval failures are not hidden by an LLM answer or confused with generator quality.
4. As a MyKnow developer, I want the evaluation to include both keyword and vector recall, so that the hybrid path and its RRF fusion are actually exercised.
5. As a MyKnow developer, I want the evaluation corpus to live in a dedicated data area, so that runtime databases and evaluation artifacts remain separate.
6. As a MyKnow developer, I want evaluation data to be inspectable and versionable as text artifacts, so that queries and relevance judgments can be reviewed without opening a binary database.
7. As a MyKnow developer, I want to provide corpus data separately from qrels, so that I can change the way judgments are generated without changing the evaluation runner.
8. As a MyKnow developer, I want qrels to identify raw child chunks with stable identifiers, so that repeated evaluation runs compare the same retrieval targets.
9. As a MyKnow developer, I want qrels to support multiple relevant chunks for one query, so that retrieval of complementary evidence is measured correctly.
10. As a MyKnow developer, I want qrels to support graded relevance, so that NDCG can distinguish core evidence from merely supporting evidence.
11. As a MyKnow developer, I want invalid qrels, duplicate identifiers, empty relevant sets, malformed queries, and invalid relevance grades to fail validation, so that scores cannot be produced from ambiguous test data.
12. As a MyKnow developer, I want the test database to be created from the normal migration contract, so that the evaluation remains compatible with the database schema without mutating business data.
13. As a MyKnow developer, I want the fixture to contain active resource versions, indexed processing runs, raw child chunks, keyword projections, and retrieval embeddings, so that the same hard filters used by production retrieval apply during evaluation.
14. As a MyKnow developer, I want the evaluation to use a real embedding provider, so that vector ranking reflects the configured embedding model rather than a synthetic mock.
15. As a MyKnow developer, I want the embedding provider, model, dimensions, and input hashes recorded in a manifest, so that stale or incompatible vector data is detected.
16. As a MyKnow developer, I want the embedding model to be explicit, so that a real-provider run cannot silently use the project’s mock model default.
17. As a MyKnow developer, I want an explicit preparation command for corpus embeddings, so that ordinary evaluation runs never rewrite evaluation data unexpectedly.
18. As a MyKnow developer, I want a failed embedding preparation to leave no partial snapshot, so that a later run cannot consume incomplete vectors.
19. As a MyKnow developer, I want normal evaluation to generate query embeddings through the configured provider, so that changes in provider behavior are observable.
20. As a MyKnow developer, I want a missing provider, unavailable endpoint, invalid response, or dimension mismatch to fail loudly, so that the suite never reports a false hybrid score after falling back to mock retrieval.
21. As a MyKnow developer, I want Recall@K to measure the share of relevant raw child chunks retrieved in the first K positions, so that coverage is quantified.
22. As a MyKnow developer, I want Hit Rate@K to measure whether at least one relevant raw child chunk appears in the first K positions, so that query-level usefulness is quantified.
23. As a MyKnow developer, I want MRR@K to measure the rank of the first relevant raw child chunk, so that early useful retrieval is rewarded.
24. As a MyKnow developer, I want NDCG@K to use graded relevance, so that the order of core and supporting evidence is distinguished.
25. As a MyKnow developer, I want every metric to be evaluated at K=1, 3, 5, and 10, so that top-result quality and the current default raw budget are both visible.
26. As a MyKnow developer, I want metric scores to stay in the 0-to-1 range, so that results are comparable across queries and K values.
27. As a MyKnow developer, I want per-query metric details, so that a poor aggregate score can be traced to specific queries and retrieved chunks.
28. As a MyKnow developer, I want macro-average scores across queries, so that one query with many relevant chunks cannot dominate the report.
29. As a MyKnow developer, I want the returned raw chunk IDs and public rank metadata preserved in the report, so that metric failures can be inspected against keyword rank, vector rank, and RRF rank.
30. As a MyKnow developer, I want the evaluation to cover keyword-only, vector-only, combined, multilingual, multi-relevant, and ranking-boundary cases, so that the hybrid implementation is not validated only by exact lexical matches.
31. As a MyKnow developer, I want the first version to report scores without invented product thresholds, so that CI gates are based on real qrels and human expectations rather than arbitrary numbers.
32. As a MyKnow developer, I want the evaluation runner to use DeepEval’s TypeScript test integration, so that the project has a standard rerunnable eval entry point while keeping metric computation deterministic.
33. As a MyKnow developer, I want the DeepEval integration to use custom deterministic metrics, so that no judge model, model credential, or unrelated network request is needed for scoring.
34. As a MyKnow developer, I want no evaluation request to write to the runtime knowledge base, so that evaluation remains safe to run repeatedly.
35. As a MyKnow developer, I want the evaluation commands and required environment variables documented, so that another developer can reproduce the run from a clean checkout.
36. As a MyKnow developer, I want future qrels generators to plug into the same data contract, so that dataset provenance can evolve independently from retrieval scoring.

## Implementation Decisions

- The highest test seam is the existing `executeRetrieval()` orchestration. The evaluation will not start the HTTP server and will not add a new production adapter solely for testing.
- The evaluation will create an isolated SQLite database after applying the project’s normal migrations. It will seed only evaluation data and will never open the runtime database for writes.
- The evaluation corpus, query set, qrels, embedding snapshot, and embedding manifest will live in a dedicated versioned evaluation-data directory, separate from runtime database files.
- The data contract will separate corpus records, query records, and qrels. Qrels will be chunk-level and will use stable fixture identifiers with relevance grades 0, 1, and 2. A grade greater than zero is relevant for Recall, Hit Rate, and MRR.
- The fixture builder will create the active resource version, indexed processing run, raw child chunks, resource knowledge-base association, and the searchable projection required by the normal raw retrieval hard filters. It will also load the prepared raw-chunk vectors into the retrieval embedding projection.
- The test will use the project’s existing real HTTP-compatible embedding provider configuration. The provider, model, dimensions, endpoint, and secret remain environment-only. The current expected provider shape is `openai-compatible` with 4096 dimensions; the model name must be explicitly configured.
- Corpus embeddings will be generated by an explicit preparation command. The preparation output will be written atomically and will include input hashes, provider, model, dimensions, and vector data. Normal evaluation will not rewrite the snapshot.
- Query embeddings will be generated through the real provider during the retrieval call. The embedding manifest must match the active provider configuration and corpus input hashes before evaluation proceeds.
- Provider configuration errors, endpoint failures, invalid vectors, dimension mismatches, unavailable services, and manifest mismatches are hard failures. The suite must not silently fall back to `mock` or continue with incomplete vectors.
- The DeepEval TypeScript SDK will be used through its Vitest integration. Each deterministic metric will be implemented as a `BaseMetric` with a configurable K and will expose a score and human-readable reason without invoking an LLM.
- The four metric families will be instantiated for K values 1, 3, 5, and 10. Recall@K will divide relevant hits by the total number of relevant qrels; Hit Rate@K will be binary per query; MRR@K will use the reciprocal rank of the first relevant result; NDCG@K will use graded gains and the ideal ordering for the query.
- The DeepEval test case will carry the query and serialized retrieval ranking as evaluation data only. It will not represent an LLM answer and will not invoke answer-oriented metrics.
- The report will preserve per-query retrieved IDs and rank metadata, then compute macro averages across queries for every metric and K. The first version will not impose product-quality thresholds.
- The first suite will exercise hybrid output only. Keyword-only and vector-only ablations may be added later as diagnostics, but are not required for this feature.
- No production schema change, retrieval algorithm change, reranker, ANN index, Wiki evaluation, graph expansion evaluation, context snapshot quality metric, or provenance quality metric is included.
- The implementation will add rerunnable preparation and evaluation commands and update the project documentation with the data contract, environment requirements, failure behavior, and clean-start workflow.

## Testing Decisions

- Good tests observe external retrieval behavior: query input, returned raw child chunk identity, rank, and public hybrid metadata. They must not call private scoring helpers or duplicate the RRF algorithm as the system under test.
- The metric math will have offline unit coverage using small deterministic rankings, including no-hit, first-position hit, late hit, multiple relevant chunks, graded relevance, and truncated-at-K cases.
- The integration evaluation will seed a clean migrated database and invoke the real retrieval orchestration with vector retrieval enabled. It will verify that raw results come only from the active indexed resource generation and that the result ranking can be scored against qrels.
- Fixture validation will cover stable identifiers, non-empty relevant judgments, valid K values, valid grades, duplicate results, malformed vectors, provider metadata mismatch, and missing explicit embedding model configuration.
- Provider preparation will cover successful snapshot creation and hard failure without partial output when the endpoint is unavailable or returns an invalid vector.
- The evaluation will verify that the runtime database remains unchanged after the suite completes.
- The repository currently has no established test suite or prior DeepEval test. The closest prior art is the existing database migration, retrieval projection rebuild, embedding-provider validation, active-generation filtering, and retrieval trace behavior; the new tests will reuse those seams and contracts rather than introducing parallel retrieval logic.
- The deterministic metric tests can run without network access. The end-to-end hybrid evaluation intentionally requires the configured real embedding service; an unavailable service is a failed precondition, not a reason to use mock data.

## Out of Scope

- Testing LLM answer generation, answer relevancy, faithfulness, hallucination, task completion, or any LLM-as-a-judge metric.
- Generating or selecting the user’s production corpus, query set, or qrels. The suite consumes the agreed contract; the data-generation workflow remains a separate decision.
- DeepEval synthetic dataset generation, Confident AI upload, hosted reports, production monitoring, or online evaluation.
- DeepEval tracing or OpenTelemetry instrumentation.
- Evaluating Wiki pages, Wiki seeds, Wiki graph expansion, provenance lookups, context snapshots, or mixed Wiki/raw context quality.
- Changing the raw hybrid ranking algorithm, tokenizer, RRF constant, chunking policy, embedding provider implementation, or database schema.
- Adding a reranker, vector index, ANN backend, or performance benchmark for large corpora.
- Adding keyword-only/vector-only baselines or automatic hyperparameter optimization in the first version.
- Setting product acceptance thresholds before real qrels and human expectations are available.
- Persisting evaluation runs or vectors into the runtime knowledge base.

## Further Notes

- The project’s current runtime configuration points at a local HTTP-compatible embedding endpoint with 4096 dimensions, but the endpoint was not running during planning and no explicit embedding model was configured. The implementation must preserve the agreed hard-failure behavior until those runtime prerequisites are supplied.
- The runtime `data` area is ignored for ordinary repository changes. The evaluation data area must remain a separate, intentional artifact location so that corpus and qrels can be reviewed and committed without mixing them with mutable runtime databases.
- The distinction between a raw child chunk, its parent context window, and a retrieval result is important: relevance is judged on the returned raw child chunk identity and rank, while parent context remains retrieval evidence rather than a separate ranked target.
- The spec intentionally does not prescribe how qrels are generated. Once the user supplies or generates the data, the same metric and fixture contract should support a real retrieval-quality run without changing the production retrieval path.
