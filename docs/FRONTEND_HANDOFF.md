# MyKnow 前端交接文档
Embedding 进度与系统日志采用 processing run 聚合和渐进展开，接口、状态和手工验证约定见 [`EMBEDDING_PROGRESS.md`](EMBEDDING_PROGRESS.md)。

> 面向：产品经理、产品 UI 设计师、前端设计师
>
> 目的：为 MyKnow 的下一轮原型设计提供统一的产品理念、用户心智模型和功能边界。
>
> 本文不规定视觉风格、颜色、字体、间距、组件库、设计 token、具体栅格或最终页面布局。设计稿可以重新组织界面，只要不破坏本文定义的产品语义和安全边界。

## 1. 产品一句话

MyKnow 是一个面向个人研究与学习的本地优先知识工作台：把零散资料沉淀为可检索、可引用、可审核、可回滚的个人知识系统。

它不是普通的文件管理器，也不是只会回答问题的聊天机器人。它要帮助用户完成一条完整链路：

```text
收集资料 → 组织知识 → 检索证据 → 让 Agent 提议整理 → 人工审核写入 → 持续维护版本
```

## 2. 目标用户与典型场景

### 目标用户

- 个人研究者：需要长期积累论文、报告、网页、笔记和研究结论。
- 学习者：需要把课程资料、阅读材料和自己的理解组织成可复用的知识结构。
- 重视来源可靠性的人：希望知道一个结论来自哪份材料、哪个版本和原文哪一处。

### 典型场景

1. 用户导入一批 Markdown、TXT、PDF 或网页资料，等待系统处理完成。
2. 用户将资料归入某个知识库或空间，用标签管理主题，并决定它是否参与 Wiki 整理。
3. 用户在限定范围内提问，得到带来源的回答；找不到证据时，系统明确说“不知道”。
4. 用户让 Agent 把资料整理为 Wiki，先看到结构、内容、引用和风险，再逐项批准写入。
5. 某份资料出现新版本后，用户看到哪些 Wiki 内容可能受影响，并决定是否更新。

## 3. 必须保持的产品理念

### 3.1 原始资料永远是事实底座

原始文件、网页快照和每个资料版本都应被视为只读材料。Wiki、摘要、标签和 Agent 产物都是建立在资料之上的派生层，不得把整理结果伪装成原文，也不得静默覆盖原始资料。

界面上应持续让用户分辨：

- 这是原始资料，还是 Wiki 派生内容；
- 这是哪个资料版本；
- 内容当前是否可用、是否仍在处理或已经失效。

### 3.2 AI 是协作者，不是自动发布者

Agent 可以阅读明确授权的范围、提取信息、提出整理建议和发现问题，但 Agent 不能直接修改 Wiki。

涉及 Wiki 写入时，用户应看到一份可理解的变更计划，包括：

- 要创建、更新或补充什么；
- 变更前后有什么不同；
- 使用了哪些证据和引用；
- 风险是什么；
- 当前是待审核、已应用、已过期还是应用失败。

因此，产品文案应使用“生成整理计划”“审阅并应用”“拒绝”“回滚”等词，不使用“AI 自动整理完成”这类会掩盖审核边界的表达。

### 3.3 结论必须能够追溯

引用不是装饰，而是答案和 Wiki 内容的可信度基础。引用至少应能指向：资料名称、资料版本、原文定位和可查看的只读原文。

用户不需要理解底层 chunk、向量或索引实现，但需要能顺畅完成：

```text
看到结论 → 打开引用 → 定位原文 → 确认上下文
```

### 3.4 “不知道”是正确结果

严格库内问答找不到足够证据时，应明确展示未知、证据不足或无法确认，而不是给出看似完整的猜测。

开放问答可以使用外部模型知识，但必须清楚区分“来自当前知识库的证据”和“模型补充内容”。

### 3.5 检索范围必须显式

每次问答和 Agent 整理都应让用户知道本次操作使用了哪些知识库、空间、资料版本或 Wiki 页面。发送前可以调整范围；发送后范围应作为本次运行的固定快照展示，避免用户无法解释答案为何出现。

### 3.6 一切重要写入都可解释、可回滚

Wiki 页面内容以版本链保存。编辑不是覆盖旧内容，而是创建新版本；恢复旧版本也应创建一个新的恢复版本。

审核记录、引用、变更 diff、应用结果和回滚记录都应保留。产品体验应让用户放心尝试，而不是害怕“一次点击毁掉原来的知识”。

### 3.7 本地优先与隐私可见

首版是单用户、本地优先的 Web 应用。知识库可以设置 AI 使用策略：允许云端、仅本地或禁止 AI；单份资料可以进一步收紧策略，实际调用采用更严格的限制。

密钥、内部配置和敏感运行信息不应出现在前端页面、普通业务记录或日志中。前端只展示对用户有帮助的能力状态，例如“当前回答使用本地模型”或“该资料禁止发送到云端”。

## 4. 领域心智模型

设计和前端实现请优先使用以下名称，避免把不同对象都叫作“文档”或“知识”。

| 产品概念 | 用户应该如何理解 |
| --- | --- |
| 知识库（Knowledge base） | 一个相对独立的研究主题或资料集合，是检索和 Wiki 的主要边界。 |
| 空间（Space） | 知识库中的组织分区，用于整理 Wiki 和缩小部分检索范围。 |
| 资料（Resource） | 用户导入的一份原始文件或网页快照。 |
| 资料版本（Resource version） | 同一份资料在某个时间点的不可变版本；更新资料会产生新版本。 |
| 处理任务（Processing task） | 对资料执行解析、分块、索引或重试的后台工作。 |
| Wiki 页面（Wiki page） | 从资料中沉淀出的可阅读、可组织、可复用的知识页面。 |
| Wiki 页面版本（Wiki page version） | 页面某次内容状态的不可变快照。 |
| 引用（Citation） | Wiki 内容或回答与资料版本原文定位之间的关系。 |
| 检索范围（Scope） | 一次问答或 Agent 运行允许读取的知识库、空间、资料版本、Wiki 页面等集合。 |
| 检索运行（Retrieval run） | 一次检索执行的记录，包含查询、范围、命中结果、来源追踪和上下文快照。 |
| Agent 运行（Agent run） | 一次回答或整理任务的执行记录。 |
| 整理计划（Change plan） | Agent 提出的、等待用户审核的 Wiki 变更集合。 |
| 影响项（Impact） | 资料版本变化后，可能需要重新检查的 Wiki 页面、章节或引用。 |

以下概念可以作为系统信息展示，但不应成为普通用户必须学习的主导航词：`Raw child chunk`、向量、FTS、embedding、RRF、processing run。它们适合出现在调试、任务详情或检索 trace 中。

## 5. 信息架构建议

首版可以沿用“三类信息并置”的工作台关系，但不要求固定为三栏：

```text
组织与范围          当前工作内容             AI 协作与系统状态
知识库 / 空间 / Wiki  资料 / Wiki / diff      Agent / 引用 / 任务 / trace
```

主导航优先覆盖：

1. 知识库与空间浏览；
2. 资料导入、更新和版本；
3. Wiki 主题树与页面；
4. 待审核的 Agent 变更；
5. 检索问答；
6. 任务、错误和审计记录。

建议保留一个稳定的知识库入口（`index / overview`）：用户回到知识库时，先看到 Wiki、资料状态、待处理影响项和最近活动，而不是被直接带到某个随机文件或空聊天页。

`log / events` 可以作为系统事件入口。它服务于追溯和排错，不应与 Wiki 内容混在一起。

## 6. Feature 交接

### 6.1 知识库、空间与标签

用户可以：

- 创建、选择和切换知识库；
- 在知识库内创建空间；
- 为资料或 Wiki 页面维护标签；
- 配置知识库的 Wiki 默认策略和 AI/隐私策略；
- 将同一份资料关联到多个知识库，不通过复制产生多个原文。

体验重点：

- 当前所处知识库必须始终清楚；
- 切换知识库时，页面、检索结果、Agent 范围和任务视图不能残留上一个知识库的内容；
- 空知识库要有明确的下一步：导入资料或创建第一篇 Wiki，而不是只显示空白。

### 6.2 资料导入与资料库

支持的资料入口：

- Markdown；
- 纯文本 TXT；
- native PDF 或 OCR PDF；
- URL 网页快照。

资料卡片或详情页应能表达：

- 名称、来源类型、原始 URL 或文件名；
- 当前版本和历史版本；
- 创建时间、更新时间和内容指纹（如需要）；
- Wiki 整理策略：可参与 Wiki、仅参与检索或继承知识库设置；
- 当前处理状态、进度、重试入口和错误摘要；
- 查看只读原文、下载原文和查看处理记录。

PDF 场景需要让用户知道是否使用 OCR，以及 OCR 处理可能带来的识别限制。上传、追加版本和重处理入口提供自动 OCR、跳过 OCR 和强制 OCR 选择，并在任务完成后明确反馈处理成功或失败及错误摘要。不要把 OCR 结果呈现为与原始 PDF 完全等价的事实；保留“原始文件”和“解析文本”之间的区别。

资料更新不是编辑原资料，而是上传或生成一个新资料版本。旧版本仍可查看和追溯。

### 6.3 Wiki 主题树与页面

Wiki 是用户日常阅读和沉淀知识的主要工作面。它应提供：

- 主题树或目录浏览；
- 页面标题、页面类型、所属空间和父子关系；
- 页面正文阅读和编辑；
- 默认模板或知识库自定义模板；
- 页面版本历史、版本 diff 和恢复；
- 页面中的资料引用及引用状态；
- 从 Wiki 内容回到原始资料定位；
- 页面之间的 Wiki link 和相关页面入口（不要求首版做知识图谱可视化）。

首版页面类型：

- `concept`：概念；
- `entity`：实体；
- `source-summary`：资料摘要；
- `synthesis`：综合或推导。

默认模板可包含：定义、核心观点、证据、争议、相关资料、待验证问题。模板是起点，不应阻止用户后续编辑。

重要语义：

- Wiki 页面是原始资料的派生层，不是原始资料的替代品；
- 用户手动编辑可以直接形成新页面版本；
- Agent 生成的页面创建和内容更新必须先进入整理计划审核；
- `index` 和 `log` 是系统入口，不应被 Agent 当作普通 Wiki 页面改写或挂载子页面。

### 6.4 引用与来源定位

引用在 UI 中应同时回答三个问题：

1. 这条内容来自哪份资料？
2. 使用的是哪一个资料版本？
3. 原文的具体位置在哪里？

支持的交互包括：

- 在 Wiki block、页面或回答旁显示引用标记；
- 展开引用详情；
- 跳转到原文片段并显示适量上下文；
- 打开原始文件或网页快照的只读版本；
- 对失效、待复核引用给出原因和后续动作。

引用状态至少需要区分：

- 正常（active）；
- 待复核（needs review）；
- 失效（broken）。

不要只显示一个“有引用”的布尔值；引用是否仍指向当前有效来源，会直接影响用户是否应该信任这段知识。

### 6.5 检索与 RAG 问答

用户可以在明确范围内发起检索或问答：

- 选择一个或多个知识库、空间、资料版本或 Wiki 页面；
- 发送前查看实际检索范围；
- 选择严格库内问答或开放问答；
- 获得带引用的回答；
- 查看使用了哪些 Wiki 页面、原始资料、资料版本和原文定位；
- 查看“证据不足/未知”的结果；
- 在必要时打开一次检索运行的详情，理解回答使用的上下文。

检索结果可以把以下来源分开呈现：

- 直接命中的 Wiki 页面；
- 与 Wiki 关系相关的邻近页面；
- 直接命中的原始资料片段。

不要用一个混合列表或一个模糊的“相关度百分比”掩盖来源差异。检索分数是排序辅助信息，不应被解释成事实置信度。

当前产品边界：空间对 Wiki 的过滤语义比对原始资料更完整；如果界面选择了空间，应避免暗示原始资料一定已被完全限制在该空间内，除非产品和数据模型先完成统一。

### 6.6 Agent 对话

Agent 对话用于两类工作：

1. **回答问题**：读取用户授权的范围，生成回答和证据引用；
2. **整理知识**：读取资料和 Wiki，输出待审核的整理计划。

对话区域应体现：

- 当前 Agent 运行状态；
- 本次对话的知识库和范围；
- 回答是库内证据、开放知识补充，还是无法确认；
- 引用数量和查看引用入口；
- 任务进行中、重试、失败和取消状态。

聊天和写入必须在心智上分开：

- 对话是读取/解释体验；
- 整理计划是变更/写入体验。

不要让用户误以为“发送一句话”就会直接改写 Wiki。

### 6.7 Agent 整理计划与审核

Agent 可提出的计划项包括：

- 创建 Wiki 页面；
- 更新 Wiki 页面；
- 给页面添加已有标签；
- 发现重复资料或重复观点；
- 发现相互冲突的事实。

每个计划项应展示：

- 操作类型和目标；
- 建议标题、页面类型和内容摘要；
- 与当前页面的 diff（如果是更新）；
- 证据和引用；
- 风险级别；
- 审核状态；
- 应用状态；
- 警告、失败原因和可执行动作。

审核操作：

- 单项批准；
- 单项拒绝并填写原因；
- 对有父子关系的树形计划审核整棵分支；
- 编辑仍待审核的建议后重新校验；
- 对低风险标签建议进行受限批量批准；
- 对已应用的安全变更执行回滚。

不能弱化的规则：

- 缺少必要证据的页面创建/更新不可应用；
- 高风险事实改写和冲突合并不能走普通批量批准；
- 父节点未成功应用时，子节点不能绕过父节点写入；
- Agent 提出的风险和 diff 不是最终事实，服务端会重新校验；
- 审核通过不等于已经写入成功。

### 6.8 资料更新与影响处理

当资料产生新版本时，系统应：

1. 保留旧版本；
2. 对新版本重新解析、分块和索引；
3. 标记可能受影响的 Wiki 页面、章节和引用；
4. 允许用户查看影响原因和来源变化；
5. 由 Agent 提议更新，用户审核后生成新的 Wiki 页面版本。

影响项不是自动更新结果。它是提醒用户重新确认的入口。

### 6.9 任务、进度与错误

后台处理可能经历导入、解析、索引、embedding、检索或 Agent 执行。前端需要提供可理解的状态反馈：

- 排队中；
- 处理中；
- 重试中；
- 已完成；
- 部分可用；
- 失败；
- 已取消。

失败状态至少要告诉用户：发生了什么、是否影响原始资料、是否可以重试、重试会做什么。Embedding 按 processing run 提供取消剩余任务和一键重试异常 chunk；重试只补跑失败、取消或缺失项，不重复成功项。原始资料不能因为派生处理失败而丢失。

“部分可用”尤其重要：例如向量检索不可用时，关键词检索仍可能正常工作；此时不应把整个知识库伪装成不可用，也不应静默隐藏能力降级。

### 6.10 运行记录与可观察性

对需要解释的操作，用户可以进入详情查看：

- 资料处理运行和尝试记录；
- Agent 运行、步骤和工具调用摘要；
- 检索运行、命中来源和上下文快照；
- 模型/Provider、耗时和失败原因（只展示必要信息）；
- Wiki 版本、审核者、时间、依据和应用结果；
- 系统事件和审计记录。

普通用户默认看到结论和行动入口，技术细节应渐进展开，避免把调试面板当成主工作流。

## 7. 状态与交互语义

### 7.1 资源状态

| 状态 | 用户含义 | 主要动作 |
| --- | --- | --- |
| 待处理 / 处理中 | 资料已保存，但还不能保证可检索 | 查看进度、等待或取消 |
| 已索引 | 当前版本可参与检索 | 查看、检索、纳入整理范围 |
| 部分可用 | 部分派生能力失败，但仍有可用能力 | 查看降级说明、重试 |
| 失败 | 当前处理未完成 | 查看错误、重试 |
| 已归档 | 用户暂时移出工作区 | 查看历史或恢复 |

### 7.2 引用状态

`active` 表示当前引用可解释；`needs_review` 表示资料变化后需要重新确认；`broken` 表示当前定位或来源完整性无法确认。待复核引用应在 Wiki、影响列表和回答来源中保持可见。

### 7.3 Agent 计划状态

审核状态和应用状态是两套状态，前端不能合并为一个“完成/未完成”：

| 维度 | 示例状态 | 含义 |
| --- | --- | --- |
| 审核 | proposed / approved / rejected | 用户是否同意这条建议 |
| 应用 | pending / applied / stale / apply_failed / rolled_back | 建议是否真正写入、是否过期、是否被恢复 |
| 证据 | used / needs_evidence / unverified / not_applicable | 当前建议的来源支持情况 |

典型状态组合：

- 已批准 + 应用失败：用户同意了，但系统没有成功写入；
- 待审核 + 已过期：建议基于旧页面版本，需要重新生成或编辑；
- 已应用 + 已回滚：曾经写入过，之后生成了恢复版本；
- 需要证据 + 待应用：应显示阻塞原因，而不是把按钮做成可直接提交。

### 7.4 写入、版本冲突与恢复

- 成功写入后再更新页面，不要先乐观地把最终内容当作已保存；
- 页面在别处产生新版本时，提示版本冲突，并提供刷新、比较或重新编辑路径；
- 恢复旧版本的动作名称应表达“恢复为新版本”，不能让用户误以为历史被删除；
- 资料删除不是首版能力，使用归档表达暂时移出工作区。

### 7.5 空状态、加载和错误

每个核心页面都需要有明确的：

- 首次使用空状态；
- 无搜索结果状态；
- 等待后台任务状态；
- 权限/隐私策略阻止状态；
- 证据不足状态；
- 失败与重试状态。

空状态应给出下一步，但不能替用户偷偷改变检索范围、自动创建内容或跳过审核。

## 8. 本轮不纳入 MVP

以下内容不应进入本轮原型的主流程，除非后续另立需求：

- 多用户协作、实时编辑和复杂权限；
- 原生移动端；
- 多 Agent 协作；
- 自动删除或覆盖原始资料；
- 网页定期自动同步；
- 知识图谱可视化；
- 手写 OCR、签名/印章识别和复杂版面理解；
- 自训练嵌入模型或排序模型；
- 学习卡片、研究报告和学习路径等扩展产品。

## 9. 原型验收关注点

原型评审时优先验证以下问题，而不是先评审颜色和装饰：

1. 用户能否在 10 秒内理解“知识库、资料、Wiki、Agent”之间的关系？
2. 用户能否明确知道当前回答使用了什么范围？
3. 用户能否从一个结论回到资料版本和原文定位？
4. 用户能否看懂 Agent 建议会改什么、依据是什么、风险是什么？
5. 用户能否区分“审核通过”和“已经应用成功”？
6. 资料更新后，用户能否找到受影响内容并决定是否处理？
7. 导入或模型失败时，用户是否知道原始资料仍然安全、下一步可以做什么？
8. 空知识库和无答案场景是否诚实、可行动，而不是制造假内容？

## 10. 交给设计阶段决定的内容

以下内容刻意不在本文锁定：

- 视觉气质、品牌表达和插画/图标方向；
- 明暗主题、颜色语义和具体色值；
- 字体、字号、行高、间距和圆角；
- 页面是三栏、双栏、抽屉、分屏还是多页面；
- 组件库、交互动画和响应式断点；
- 编辑器是 Markdown、所见即所得或混合模式；
- 检索结果和引用在页面中的具体呈现形式。

设计自由的前提是：不隐藏来源、不混淆版本、不绕过范围确认、不把 Agent 提案当成已写入事实。
